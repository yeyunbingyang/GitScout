# 1. 产品概述

GitScout 是一个面向 GitHub 开源项目发现、趋势观察与长期研究的采集工作台。系统以 GitHub Trending 的日榜、周榜、月榜作为周期趋势来源，同时建立独立的 Stars 总榜实时采集能力，将短期趋势榜单与全站累计 Stars 排名分开管理。

## 1.1 产品目标

- 自动采集 GitHub Trending 日榜、周榜、月榜，并保留每次采集的历史快照。

- 提供一个统一的周期榜单导航，在页面内部切换日榜、周榜、月榜并查询历史采集结果。

- 建立独立的 Stars 总榜，按 GitHub 当前累计 Stars 排序，通过手动刷新或定时刷新获取最新数据。

- 支持跨周期排名比较、项目感兴趣标记、历史轨迹查询和采集任务追踪。

- 为后续开源项目介绍、核心功能演示、项目可视化展览及 Remotion 讲解视频提供项目数据基础。

## 1.2 核心产品原则

| **原则**           | **说明**                                                                       |
|--------------------|--------------------------------------------------------------------------------|
| 统一项目主数据     | 同一仓库以 GitHub repository_id / full_name 识别，不因进入多个榜单而重复建档。 |
| 周期快照不可覆盖   | 每次日 / 周 / 月采集均保存独立快照，历史排名可追溯。                           |
| Stars 总榜独立采集 | Stars 总榜不依赖 Trending 榜单的项目集合，单独向 GitHub 查询当前仓库排名。     |
| 采集与展示分离     | 前端负责筛选、展示和触发任务；后端负责调度、API 请求、持久化、限流与重试。     |
| 数据来源透明       | 每个结果应能区分实时 API 数据、历史快照数据和原型演示数据。                    |

左侧导航按用户确认的结构收敛。日榜、周榜、月榜只保留一个导航入口，不拆成三个独立导航。

| 周期榜单     | 日榜 / 周榜 / 月榜               | 单一导航入口；进入页面后用顶部周期切换器切换。历史快照选择器位于榜单页面内。        |

| 采集记录     | 任务执行历史                     | 查看任务类型、执行时间、状态、耗时、入库数量与错误信息。                            |
| 采集设置     | 周期调度 / Stars 刷新 / 数据管理 | 配置采集频率、来源、范围、重试、快照保留等。                                        |

## 2.1 周期榜单页面

- 顶部提供日榜、周榜、月榜三个切换项；切换周期时不离开当前导航页面。

- 周期页面提供历史快照选择器，列出该周期已成功保存的采集批次及采集时间。

- 支持回到最新快照；历史快照查询直接读取数据库，不重新访问 GitHub。

- 榜单列表支持项目名称搜索、语言筛选、主题筛选、排名排序、Stars / 增量排序。

- 榜单行展示排名、仓库名称、简介、语言、Stars、Forks、当期 Stars 增量、标签与感兴趣状态。

- 打开项目详情可查看基础信息、日 / 周 / 月排名、Topics、License、更新时间及 GitHub 仓库入口。

## 2.2 历史快照查询方式

| **查询入口** | **行为**                                                   |
|--------------|------------------------------------------------------------|
| 周期切换     | 先选日榜 / 周榜 / 月榜，再显示对应周期的历史采集批次。     |
| 按采集日期   | 选择某次采集时间，载入该次快照的完整原始排名。             |
| 按仓库搜索   | 输入 owner/repo 或关键词，查看该项目在哪些历史快照中出现。 |
| 按排名范围   | 筛选 Top 10 / Top 50 / Top 100 或自定义排名区间。          |
| 历史对比     | 选择两个快照，比较新增、掉榜、排名上升和下降的仓库。       |

# 3. Stars 总榜：独立实时采集

| Stars 总榜是独立的数据源和采集任务。它不是“把日榜 / 周榜 / 月榜合并后按 Stars 排序”，而是直接向 GitHub 查询公开仓库，并按当前累计 Stars 降序展示。 |
|----------------------------------------------------------------------------------------------------------------------------------------------------|

## 3.1 页面功能

- 提供“立即采集”操作，触发一次新的 GitHub 仓库搜索请求。

- 支持进入页面时刷新，以及可配置的定时刷新间隔；原型提供手动、15 分钟、30 分钟、1 小时、6 小时选项。

- 展示最近同步时间、同步状态、数据来源、当前查询结果数量和榜首 Stars。

- 默认按 Stars 从高到低排序；支持 Stars 升序、Forks 排序及近期 Stars 增量排序。

- 支持按主要语言、Topics / 主题筛选。

- 提供“曾上过趋势榜”和“跨周期上榜”筛选，作为本地历史数据与实时搜索结果的交集视图。

- 支持分页、每页数量设置、CSV 导出、项目详情与感兴趣标记。

- 每次成功刷新应保留一次 Stars 采集快照，以便后续计算 Stars 增长与排名迁移。

## 3.2 实时采集的定义

本项目中的“实时”指用户手动触发或系统按配置间隔发起新请求，获取 GitHub API 在该次请求时返回的当前仓库 Stars 数据。它不是 GitHub 事件流，也不意味着 Stars 数量发生变化时毫秒级推送。页面需明确展示“最近同步时间”，并避免将缓存数据标记为刚刚实时获取。

## 3.3 GitHub API 方案与限制

| **项目**     | **需求 / 技术约束**                                                                                                 |
|--------------|---------------------------------------------------------------------------------------------------------------------|
| 主要接口     | GET https://api.github.com/search/repositories                                                                      |
| 排序参数     | sort=stars&order=desc                                                                                               |
| 查询参数     | 初始建议 q=stars:\>0；可按 Stars 区间切片查询。                                                                     |
| 分页         | per_page 最大 100；使用 page 分页。                                                                                 |
| 单次搜索上限 | Search API 每个查询最多返回 1,000 条结果；不能将其描述为无上限全站榜单。                                            |
| 搜索范围限制 | GitHub 文档说明单个查询最多搜索 4,000 个匹配仓库；结果可能因查询耗时而标记 incomplete_results。                     |
| 扩展策略     | 如需超过单查询结果上限，按 Stars 区间 / 语言等条件分片，合并后按 repository_id 去重；仍需展示覆盖范围与采集完整性。 |
| 速率限制     | Search 端点有独立限流：认证请求每分钟最多 30 次，未认证请求每分钟最多 10 次；还需遵守 REST API 主限额。             |
| 错误处理     | 读取 Retry-After、X-RateLimit-Remaining、X-RateLimit-Reset；遇到限流采用退避重试，禁止无间隔持续重试。              |

建议请求示意：

GET /search/repositories?q=stars%3A%3E0&sort=stars&order=desc&per_page=100&page=1

## 3.4 实时榜单的数据完整性

- 页面需区分“当前查询结果范围”与“全 GitHub 所有仓库”；默认首期定位为可解释的高 Stars 排名结果集。

- 当 API 返回 incomplete_results=true 时，必须显示结果可能不完整的提示。

- 分片采集时记录每个查询分片、时间、总数、返回数、失败原因和合并去重数。

- 若请求被限流或部分分片失败，不能将未完成结果标记为完整总榜。

- 每次刷新记录采集时间与结果快照，Stars 增量按同一仓库相邻两次成功采集计算。

# 4. 趋势总览与周期对比

## 4.1 趋势总览

- 本周期收录项目数、新晋上榜数、跨周期热门项目数、已感兴趣项目数。

- 日 / 周 / 月趋势热度走势，可切换周期查看对应统计。

- 主要语言分布、热门 Topics / 技术方向分布。

- 跨周期热门项目表，显示同一仓库的日榜、周榜、月榜排名。

- 从总览快速跳转周期榜单、周期对比或感兴趣项目。

## 4.2 周期趋势对比

- 以 repository 为行，日榜 / 周榜 / 月榜为列，展示对应排名。

- 支持筛选三榜均上榜、指定周期上榜、排名持续上升等项目。

- 展示连续上榜周期数、排名迁移和趋势判断。

- 支持勾选至少两个项目进行对比，并可导出对比结果。

- 排名缺失表示该项目未进入该次快照的采集范围，不应直接推断项目热度为零。

# 5. 感兴趣标记与项目详情

## 5.1 感兴趣项目

- 从榜单卡片、榜单表格和项目详情中添加 / 取消感兴趣标记。

- 感兴趣状态支持持续观察、待研究、已研究等分类状态。

- 感兴趣标记列表支持搜索、筛选、排序和 CSV 导出。

- 感兴趣标记记录关联 repository 主表，不复制项目基础信息。

## 6.2 调度与设置

- 日榜、周榜、月榜分别配置启用状态、执行时间与时区。

- Stars 总榜配置进入页面自动刷新、定时刷新间隔、单次目标数量和分片策略。

- 采集来源分别维护 Trending 页面地址与 Stars API 地址。

- 支持采集失败自动重试，最大重试次数与退避间隔可配置。

- 配置历史快照保留期限；默认建议保留原始快照，若设置清理策略必须明确提示。

- 提供 GitHub API 认证配置入口；Token 仅由后端安全保存，不写入前端 HTML、浏览器存储或日志。

# 8. 关键业务流程

## 8.1 周期榜单采集流程

1.  调度器按日 / 周 / 月计划触发对应采集任务。

2.  采集器读取对应 GitHub Trending 页面，解析仓库名称、排名、Stars 增量等字段。

3.  通过 repository full_name / GitHub ID 进行主表匹配；不存在则创建，存在则更新当前基础信息。

4.  创建新的 trending_snapshots 记录，并写入本次所有 trending_snapshot_items。

5.  任务完成后更新状态、数量和耗时；前端历史快照列表可查询该批次。

6.  若采集失败，记录异常；失败任务不得生成“成功”快照。

## 8.2 Stars 总榜实时采集流程

7.  用户点击“立即采集”，或后端调度器到达自动刷新时间。

8.  后端生成 Search API 查询计划，按页请求；必要时按 Stars 区间切片。

9.  逐批处理响应，记录 incomplete_results、限流信息和分片状态。

10. 将仓库基础信息 upsert 到 repositories；将本次排名与 Stars 数量写入 stars_scan_items。

11. 全部分片结束后计算完整性状态：成功、部分成功或失败。

12. 前端刷新榜单、显示最近同步时间、覆盖范围与数据完整性提示。

# 10. 验收标准

- 左侧导航中日榜、周榜、月榜只出现一个“周期榜单”入口。

- 进入周期榜单后，可在日榜、周榜、月榜之间切换，且切换不增加左侧导航项。

- 每个周期均可选择历史快照；选择历史快照后显示对应采集批次的原始排名。

- 历史快照查询不触发重新采集；没有历史记录时显示空状态，不伪造日期和数量。

- Stars 总榜有独立导航入口、独立采集任务和独立历史扫描记录。

- Stars 总榜默认按 Stars 降序；语言、主题、排序、分页和 CSV 导出有效。

- Stars 总榜刷新后显示真实的最近同步时间；API 未接入时明确标记演示数据 / 未连接。

- Stars API 返回不完整、限流或部分分片失败时，页面不能显示为完整成功。

- 同一 repository 在多个周期、多个 Stars 扫描中关联同一主表记录。

- 周期快照和 Stars 扫描快照互不覆盖，可分别查询和比较。

- 感兴趣标记、项目详情、周期对比、采集日志和设置页面均可正常使用。

# 16. 智能推荐与综合评分模型

智能推荐用于从 Stars 总榜与日 / 周 / 月 Trending 历史快照中发现值得进一步关注的仓库。推荐分是热度与持续上榜信号的综合排序，不代表项目质量、安全性、维护质量或与用户实际需求的匹配程度。

## 16.1 候选项目池

- 候选项目池由最近一次成功 Stars 总榜采集结果，以及评分窗口内出现过的日榜、周榜、月榜仓库去重合并构成。

- 以 GitHub repository_id 作为主关联标识；无 ID 的早期数据可用规范化 owner/repo 作为临时唯一键，后续回填 repository_id。

- 候选池需要显示覆盖范围与最近数据时间；Stars 总榜只覆盖已采集范围时，不得将推荐列表描述为完整 GitHub 全站项目。

- 项目从某个周期榜单掉榜，不删除其项目主记录，也不清除既有感兴趣标记或研究记录。

## 16.2 默认权重与公式

推荐系统采用 100 分制。建议初始默认权重如下，兼顾长期影响力、短期爆发、中期持续性和长期稳定性。

| **评分维度**   | **默认权重** | **解释**                                             |
|----------------|--------------|------------------------------------------------------|
| Stars 总榜表现 | 30%          | 当前累计 Stars 排名百分位，反映项目长期关注度。      |
| 日榜上榜表现   | 15%          | 最近 30 次成功日榜快照的上榜比例，捕捉短期热度。     |
| 周榜上榜表现   | 30%          | 最近 12 次成功周榜快照的上榜比例，反映中期持续性。   |
| 月榜上榜表现   | 25%          | 最近 12 次成功月榜快照的上榜比例，反映长期趋势沉淀。 |

R = 0.30 × S_stars + 0.15 × S_daily + 0.30 × S_weekly + 0.25 × S_monthly

其中 R 为综合推荐分；各 S 指标均转换为 0～100 分。最终分数保留一位小数，排序以未四舍五入的原始计算值为准。

## 16.3 各指标归一化方式

| **指标**   | **计算方式**                                                                                | **统计窗口**                                       |
|------------|---------------------------------------------------------------------------------------------|----------------------------------------------------|
| Stars 得分 | 在当前候选池按 Stars 降序排名，使用百分位：100 × (N - rank + 1) / N。N 为候选池去重项目数。 | 最近一次成功 Stars 总榜采集及候选池当前 Stars 数据 |
| 日榜得分   | 日榜上榜次数 ÷ 最近窗口内成功日榜快照数 × 100。                                             | 最近 30 次成功日榜快照                             |
| 周榜得分   | 周榜上榜次数 ÷ 最近窗口内成功周榜快照数 × 100。                                             | 最近 12 次成功周榜快照                             |
| 月榜得分   | 月榜上榜次数 ÷ 最近窗口内成功月榜快照数 × 100。                                             | 最近 12 次成功月榜快照                             |

示例：某项目在最近 30 次成功日榜采集中出现 18 次，则日榜得分为 18 ÷ 30 × 100 = 60 分。周榜 8 / 12 次为 66.7 分，月榜 7 / 12 次为 58.3 分。

## 16.4 权重预设

| **方案**         | **Stars** | **日榜** | **周榜** | **月榜** | **适用场景**                               |
|------------------|-----------|----------|----------|----------|--------------------------------------------|
| 综合平衡（默认） | 30%       | 15%      | 30%      | 25%      | 兼顾影响力、短期热度与长期持续性。         |
| 趋势发现优先     | 20%       | 25%      | 35%      | 20%      | 更关注近期快速上升和中期持续出现的新项目。 |
| 长期价值优先     | 40%       | 10%      | 25%      | 25%      | 更重视累计关注度和长期稳定趋势。           |

原型提供权重方案切换。正式系统应允许管理员维护权重预设；每次计算都保存实际权重，避免同一历史推荐结果因后续权重变化而无法复现。自定义权重可作为后续扩展，四项权重之和必须为 100%。

## 16.5 数据不足、置信度与边界

- 分母只统计成功快照；失败、取消、部分失败且未形成可用快照的任务不得进入有效样本分母。

- 当某指标没有可用数据，标记为 N/A，不得按 0 分处理；计算时将可用指标权重按比例重新归一化，并显示“数据不足”提示。

- 建议最低有效样本：日榜至少 10 次、周榜至少 4 次、月榜至少 3 次；低于门槛时该项暂不计分，显示实际样本量。

- Stars 数据过期或最新 Stars 扫描不完整时，显示数据时间与完整性标识；不得静默使用旧值冒充实时值。

- 并列排序依次按综合分、Stars 排名、最近一次上榜时间排序。

- 日 / 周 / 月上榜信号存在相关性，权重是产品偏好而非统计独立性证明；推荐分只用于项目发现，不作为质量结论。

## 16.6 推荐等级与理由

| **分数区间** | **推荐等级** | **用途**                             |
|--------------|--------------|--------------------------------------|
| 85–100       | 优先研究     | 优先进入研究候选队列。               |
| 75–84.9      | 强烈推荐     | 建议重点关注，可加入研究。           |
| 65–74.9      | 值得关注     | 保持观察，结合项目实际需求判断。     |
| 50–64.9      | 观察         | 作为备选项目或后续跟踪。             |
| 0–49.9       | 低优先级     | 当前热度信号较弱，不代表项目质量差。 |

推荐列表应展示综合分、四项子分、上榜次数 / 有效快照数、权重方案及推荐理由。推荐理由由贡献较高的指标生成，例如“Stars 排名靠前”“近期日榜活跃”“周榜持续上榜”“月榜长期沉淀”。

建议提供“全部推荐、优先关注、新兴潜力、长期稳定”等筛选。新兴潜力可按日榜得分较高且 Stars 得分尚未进入高位识别；长期稳定可按周榜与月榜得分同时较高识别。具体阈值应可配置。

## 16.7 推荐计算留痕

- 每次生成推荐结果创建 recommendation_runs 记录，保存计算时间、算法版本、权重方案、具体权重、候选池范围、数据截止时间与有效快照数。

- 每个项目保存 recommendation_scores 明细，包括四项子分、总分、排名、推荐理由代码与数据覆盖信息。

- 新快照或权重方案变化后可以重新计算；旧推荐批次保留，不覆盖历史计算结果。

- 推荐分的变化可用于后续分析，但不得回写修改原始 Stars 或 Trending 快照。

# 17. 感兴趣标记与项目研究工作区

发现、兴趣和研究是三个不同阶段：推荐页负责发现；感兴趣标记用于轻量保存；项目研究工作区负责持续分析。感兴趣标记与加入研究相互独立，用户可以只标记感兴趣而暂不研究。

## 17.1 标记感兴趣

- 智能推荐、Stars 总榜、周期榜单和项目详情均提供“标记感兴趣 / 已感兴趣”操作。

- 标记后项目进入“感兴趣项目”页；再次操作可取消标记。

- 感兴趣项目页支持搜索、导出，以及“尚未加入研究 / 已加入研究”筛选。

- 标记感兴趣不自动创建研究记录；是否进入研究工作区由用户单独决定。

- 取消感兴趣不应自动删除已有研究记录。

## 17.2 加入项目研究

- 智能推荐、Stars 总榜、周期榜单和项目详情提供“加入研究”操作。

- 加入后在 research_projects 创建一条研究记录，默认状态为“待研究”，默认优先级为“中”。

- 同一仓库不可重复加入；已加入时显示“已加入研究”。

- 移出研究工作区只删除 / 归档研究关系，不影响 repositories 主表、历史榜单快照和感兴趣标记。

- 项目可从待研究进入研究中、已完成或暂缓；状态变更应保留更新时间。

## 17.3 研究状态与研究记录

| **字段**   | **要求**                                                               |
|------------|------------------------------------------------------------------------|
| 研究状态   | 待研究、研究中、已完成、暂缓。                                         |
| 优先级     | 高、中、低；用于研究队列排序，不影响推荐分。                           |
| 研究目标   | 说明为什么研究该项目、希望验证什么问题。                               |
| 研究记录   | 记录核心功能、技术架构、关键依赖、部署体验、优缺点、许可证与安全观察。 |
| 下一步行动 | 记录下一项可执行任务，例如阅读 README、部署运行、分析源码模块。        |
| 研究结论   | 完成研究后总结适用场景、技术价值、风险和是否值得采用。                 |
| 时间字段   | 加入时间、开始时间、最近更新时间、完成时间。                           |

研究页采用项目卡片 / 列表管理，每个项目可直接编辑状态、优先级、研究笔记和下一步行动，并保存记录。后续可扩展独立研究详情页、Markdown 笔记、源码分析、架构图、功能演示与 Remotion 视频产物。

## 17.4 研究工作流

13. 在智能推荐或榜单中发现项目。

14. 标记感兴趣，项目进入感兴趣项目列表。

15. 确认值得研究后，点击“加入研究”。

16. 在项目研究页设置优先级、研究状态和研究目标。

17. 逐步补充核心功能、技术架构、部署记录、优缺点与研究结论。

18. 完成后将状态设为“已完成”；需要以后再看可设为“暂缓”。

## 17.5 验收标准

- 推荐页默认使用综合平衡权重，四项权重合计 100%，切换方案后分数与排名即时重算。

- 每个推荐项目均可查看 Stars、日榜、周榜、月榜子分、上榜次数和推荐理由。

- 同一批候选项目在同一权重、同一数据截止时间下应得到可重复的评分结果。

- 某周期没有有效采集数据时，该项显示 N/A，不按零分处罚；低于最低样本数时显示数据不足。

- 可以在推荐页标记 / 取消感兴趣，且感兴趣项目页数量与列表同步更新。

- 可以将项目加入研究；重复添加不会产生重复研究记录。

- 研究页支持状态、优先级、研究笔记、下一步行动编辑与保存。

- 移出研究不影响感兴趣标记；取消感兴趣不影响既有研究记录。

- 研究记录导出包含项目、状态、优先级、笔记和下一步行动。

- 推荐分只表达热度信号，不得在 UI 中描述为项目质量、安全或成熟度评分。
